Same code, four layers

1 · HTML

A document

Adds: formatted text, links, menus, video.

Runs: the browser handles the built-in stuff.

Limit: only does what's built in.

2 · GitHub

Published

Adds: a link anyone in the world can open.

Runs: nothing. GitHub Pages only hands out files.

Limit: just files, no processing.

3 · JavaScript

Interactive

Adds: logic, graphics, games, tools.

Runs: on each visitor's own computer, in their browser.

Limit: anything saved stays in that one browser.

4 · Cloudflare

An app

Adds: logins, saved data, data shared between people.

Runs: on Cloudflare's servers, with a database.

Now: it remembers, on any device.

Same HTML. Same JavaScript. What changes is where it's stored and where it runs.

GitHub Pages: files in, site out

Free + simple

Every commit republishes your site.

No processing

It just hands out files. Nothing runs on GitHub's side.

So it can't…

save data, check a login, or share anything between visitors.

Layer 3 · JavaScript runs on your computer

The host just sends files. Your browser has a JavaScript engine built in, and it runs the code on your processor.
Heavy page? Your fan spins up. Close the tab and it stops.

Why JavaScript, not Python?

In the browser

HTML, CSS and JavaScript. JavaScript is the only language every browser runs.

On a server

JavaScript, Python and almost anything else.

Python in a browser?

Possible with add-ons, but heavy and slow to load. So Python usually lives on a server or your own machine.

Three places data can live

Cache

A temporary copy of the site's files, so it loads faster. The thing a hard refresh clears.

Local storage

A page saves your stuff, like a to-do list or settings. Survives closing the tab, but only in this browser on this computer.

Database

Saved on a server. Follows you to any device, and can be shared with other people. Needs a host like Cloudflare.

Layer 4 · Cloudflare is everywhere

A network of servers in hundreds of cities. It watches your repo and copies your site out on every push.
Each visitor gets the closest copy, so it's fast everywhere.

Two kinds of hosting: files or code

Hands out files

GitHub Pages. Everyone gets the same file. Anything saved stays in that visitor's browser.

Runs code

Cloudflare Workers. Builds an answer for each visitor: checks a login, saves to a database, sends back their data.

Same HTML and JavaScript on the page. The difference is what's behind it.

You click Save. Where does it go?

  1. Your browser sends it to a Worker, a small piece of code on Cloudflare.
  2. The Worker checks who you are and saves it to a database.
  3. Open the site on your phone: the Worker sends the same data back.

Why real sites use a host like this

Your own domain

Fast everywhere

Preview links

Private code

Your repo can stay private. Only the site is public.

Sites become apps

Small bits of server code and a database on the back end: forms, saved data, logins.

Three paths. One pipeline.

Pick the path. Everyone lands in a repo, a commit history and a live link.

Path 1: By hand

  • Keep building your site, no AI
  • Pull ready-made blocks from the block library: banner, cards, gallery, table, FAQ, contact
  • Paste them in, then make them yours: words, images, your brand
  • Any idea you want. A simple site, done well.
You can say you hand-coded every line.

Path 2: Mix

  • Your hand-built site, plus AI-added pieces
  • Use an AI helper: GitHub's built-in Copilot chat, or Claude or ChatGPT in a browser tab
  • Use the HTML-3 move: one block, plain code, scoped to its box
  • Above every AI piece, a comment in your own words saying what it does
If you can't explain it, it doesn't go in.

Path 3: Full build. More power, higher bar.

The setup

Claude Pro (or ChatGPT) connected to your GitHub, deployed through Cloudflare.

The catch

You don't build "a cool site." You build a learning tool that teaches Path 1 concepts.

Why

To build a tool that teaches it, you have to understand it. The AI can't do that part for you.

No live link on Settings → Pages?

When it works, the top of that page says "Your site is live at…" with your link. No link means GitHub hasn't built your site. Check in this order:

  1. Source says "Deploy from a branch"? Not "GitHub Actions". Pick main and / (root), then Save.
  2. Email verified? Go to github.com/settings/emails. "Unverified" means click Resend, then verify.
  3. Actions allowed? Settings → Actions → General → Allow all actions → Save.
  4. Kick it: edit one word in README.md, commit, wait 2 minutes, refresh Settings → Pages.
  5. Still no link? Check the Actions tab for a red X, then show me.

Committed, but nothing changed?

A change usually shows in 1–2 minutes. You can't speed GitHub up, but you can find what's in the way:

  1. Old copy in your browser? Hard-refresh (Ctrl+Shift+R / Cmd+Shift+R) or open your link in a private window.
  2. Still building? Actions tab: yellow means wait, red means it failed. Click it to see why.
  3. Committed to a new branch? Your change must be on main. Pick "Commit directly to the main branch".
  4. Right file, right repo? You changed index.html, and the link you're opening is this repo's.

Habit: always check your live site in a private window.
